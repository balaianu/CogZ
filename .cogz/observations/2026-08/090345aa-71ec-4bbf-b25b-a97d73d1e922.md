The original `find_parent_path` function in `expand.rs` called
`get_edge_type_between` for each frontier node until it found the
parent of a newly discovered neighbor. This was O(frontier_size)
SQL queries per neighbor — a classic N+1 pattern.

**Impact at current scale:** Negligible. Small repos, 2-hop max,
sparse graphs. The BFS typically has 1-5 frontier nodes.

**Impact at Phase 8 scale:** Significant. Code indexing produces
denser graphs (functions calling functions, imports, extends).
A frontier of 20+ nodes with 50+ neighbors would issue 1000+
queries per hop.

**Fix:** Replaced with `get_edges_involving_batch` — a single
query per BFS hop that returns all (source, target, edge_type)
triples touching the frontier. Parent-child relationships are
determined in Rust from the edge list.

This was caught during the Phase 5 review, not during testing.
The tests passed because the N+1 pattern produces correct results,
just slowly. Performance issues need code review, not just test
coverage.
